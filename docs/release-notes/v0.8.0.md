# v0.8.0 — Local mode on Windows

The headline: **Windows x64 now runs the full local stack.** Speech
recognition, intent classification and the German voice all run on your own
machine — no API key, no cloud round trip. Alongside it, a fix to the macOS
audio input path that had been quietly degrading speech recognition on
*every* backend.

---

## ⚠️ Before you update

### Everyone on Windows: check the Visual C++ Redistributable

The plugin itself needs nothing, but the bundled `piper.dll` and
`onnxruntime.dll` require the **Microsoft Visual C++ 2015–2022
Redistributable (x64)**. Most systems already have it — X-Plane 12 and
practically every game installs it — so this rarely bites.

It is worth knowing the symptom, because it is easy to misread: the plugin
loads normally, the cloud modes work fine, and only the **first ATC voice
playback** fails, with `0xC06D007E` in `Log.txt`. If you see that, install
the redistributable from Microsoft before investigating anything else.

### Upgrading from v0.6.0 or older: one orphaned file

v0.6.1 renamed the plugin folder and the plugin binary from
`xp_wellys_devfr_atc` to `xp_wellys_vfr_atc`. The updater only manages files
it knows about — the same rule that protects your ~2 GB of downloaded models
— so the old binary was never removed, and X-Plane has been loading **both**
copies ever since. If the updater kept reporting a new version while the
plugin's own window showed an older one, this was why.

**Via the SkunkCrafts Updater:** nothing to do. This release removes the
orphan automatically.

**If you install by unzipping manually:** the ZIP unpacks as
`xp_wellys_vfr_atc/`, so it lands *beside* any old `xp_wellys_devfr_atc/`
folder rather than replacing it, and you end up running two plugins. Delete
the old folder:

```
X-Plane 12/Resources/plugins/xp_wellys_devfr_atc/     <- delete this
X-Plane 12/Resources/plugins/xp_wellys_vfr_atc/       <- keep this
```

Your API keys, settings and downloaded models are not affected — keys live in
the OS credential store, and models are re-used from the new folder once you
point the Models tab at them (or simply re-download).

Anyone who first installed **v0.6.1 or later** was never affected.

## New

**Local mode on Windows x64.** whisper (speech recognition) and Llama (intent
classification) run on the **Vulkan** GPU backend; the German Piper
`de_DE-thorsten` voice runs on the CPU. Response times are comparable to
Apple Silicon.

Vulkan rather than CUDA is deliberate: `vulkan-1.dll` ships with your
graphics driver, so there is no multi-hundred-megabyte GPU runtime to
download, and AMD and Intel GPUs are covered too. The trade is roughly
10–30 % less throughput than CUDA on the same card, and the models share VRAM
with X-Plane's own renderer. Where no Vulkan compute device is available — as
on some virtualised cloud PCs — it falls back to CPU rather than failing.

The models (~2 GB) are not bundled. Download them in-sim from the **Models**
tab, exactly as on macOS.

All three backends — Local, OpenAI and Mistral — now work on both platforms
from the same binary. The mode is a runtime setting.

## Fixed

**macOS: speech recognition was degraded by the audio input path.** The
capture layer adopted the microphone's native rate (typically 48 kHz) and
converted to the 16 kHz the recognisers expect using unfiltered linear
decimation. Without a low-pass filter, everything above 8 kHz folds back into
the speech band — and 4–10 kHz is precisely where the sibilants live that
distinguish spelled callsigns. "Foxtrott", "Oscar" and "Sierra" collapsing
into each other was the expected signature.

macOS now asks Core Audio for 16 kHz directly, so the system's own
band-limited converter does the work, and the software fallback (still used
by devices that refuse a 16 kHz format, such as some Bluetooth headsets) is a
proper windowed-sinc converter.

This affected **all three backends on macOS**, not just Local: the conversion
happens before the audio reaches any recogniser, so OpenAI and Mistral
received the same aliased input. Windows was never affected.

Honest caveat: the mechanism is proven and covered by a regression test, but
the actual improvement in recognition accuracy has not yet been measured.

**Windows: the Piper voice crashed on first use.** Two independent bugs that
occurred stacked, so each fix only changed the error code and looked like a
failure. The bundled library declared an ONNX Runtime environment at
namespace scope, whose constructor ran under the Windows loader lock and
crashed there; and the delay-load helper resolved DLLs against a search path
that does not include the plugin's own directory. Both are fixed
(`xp_wellys_libs` 0.4.2 plus an explicit preload by absolute path).

A failure in the voice engine now also degrades gracefully with a diagnostic
instead of taking the plugin down.

## Maintenance

Added `make verify-install`, which CRC32-compares an installed tree against
the published update files and names anything stale. The updater records its
version in a config file it writes itself, so it can report a successful
update even when a file replacement did not happen — this makes that visible
instead of leaving it to guesswork.

`make release` now refuses to run unless you are on `main` and up to date
with the remote, so a release tag cannot accidentally be cut from an older
tree.
